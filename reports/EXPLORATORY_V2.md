# 탐색 실험 v2 — 단일 언어 학습량 200k→900k (연구 증거 아님)

탐색 v1과 **학습량만** 다르다. EN·DE·KO 단일 언어 런을 같은 시드 20001, 같은 데이터(`draft-v4.3`)·토크나이저·실제 cb5k 배선·모델·학습률·임계값(0.80)·평가 간격으로, 단일 언어 상한만 200,000→900,000으로 올려 새로 실행했다. 코드 해시 `6df7331008bb4b20…`(v1과 동일), 프로토콜 `configs/protocol-v4-ai-mono900k.json`(v1 프로토콜과 `version`·`mono_cap`만 다름을 스크립트가 검사). 검수 기록이 불완전한 상태의 예비비 탐색 실험이며, 인증·pilot-ready·G2/G3를 통과한 것이 아니고 언어 우열 결론을 내지 않는다. 기존 v1 런·체크포인트·데이터는 수정하지 않았다(39개 파일 SHA-256 평가 전후 동일). **test 분할은 어디에도 쓰지 않았다.**

재현 도구: `scripts/exploratory_mono_exposure.py` (`--plan`, `--execute [--retry]`, `--evaluate`). 수치: `reports/exploratory-v2-report.json`. 런 산출물: `runs/exploratory-v2/` (저장소 미포함).

## 방법

- 각 런은 공식 학습 루프(`flystudy.train.run`, smoke 코호트, CUDA)를 4단계로 나눠 실행했다. 단계 경계는 루프의 디버그 업데이트 상한(`max_updates`)으로 멈추고, 다음 단계는 루프의 장애 복구 `resume`으로 이어진다. 배치는 항상 256개(10240 = 40×256)이므로 업데이트 수가 곧 노출량이다. `src/`는 수정하지 않았다.
- 보존 체크포인트: 781 업데이트 = **199,936** 노출, 1,172 = **300,032**, 2,344 = **600,064**, 3,515 = **899,840**. 900k 단계는 상한(900,000) 한 업데이트(160 노출) 전에 멈춰, 상한 도달 시 자동으로 실행되는 독립 시험(test) 경로를 타지 않았다. `primary.pt`·`independent-test.json`은 세 런 모두 생성되지 않았다.
- 정기 dev A/B 패널(원본 문장, 10,240 노출마다)은 루프가 그대로 수행했다. 어느 런도 숙달(0.80 연속 2회) 조건에 이르지 않았다(정기 패널 최고치 0.51–0.56).
- 평가(`--evaluate`, 파라미터 갱신 없음, `immutable_evaluation`): 고정 학습 문항 표본(과제당 1,000, 세 언어에 같은 meaning_id·label, id 목록 sha256 `aa43624e…`), 평서문(`assertion_view`) dev A/B, 원본 dev A/B. 비교용으로 v1 단일 200k `primary.pt` 3개와 v1 혼합 900k `primary.pt`도 같은 세트로 평가했다.

## 실행 기록·비용

| 런 | 장치 | 1차 시도 | 2차 시도 (재개) | 최종 | 손실 처음→끝 (781/1172/2344 업데이트 시점) | 실제 GPU시간 |
|---|---|---|---|---|---|---:|
| explore-v2-mono-en | cuda:0 | 200k 단계 완료 후 재개 실패 (0.018 h) | 200k 체크포인트에서 900k까지 (0.055 h) | 899,840 노출 / 3,515 업데이트 | 0.699→0.060 (0.690 / 0.679 / 0.191) | 0.073 h |
| explore-v2-mono-de | cuda:1 | 동일 (0.020 h) | 동일 (0.078 h) | 899,840 / 3,515 | 0.698→0.258 (0.695 / 0.697 / 0.675) | 0.098 h |
| explore-v2-mono-ko | cuda:0 | 동일 (0.020 h) | 동일 (0.063 h) | 899,840 / 3,515 | 0.695→0.0004 (0.145 / 0.024 / 0.002) | 0.083 h |

- **1차 시도 실패 원인**: `train.py`의 resume 경로가 체크포인트를 `map_location=<cuda>`로 읽어 저장된 CPU RNG 상태 텐서가 GPU로 옮겨지고, `torch.set_rng_state`가 `RNG state must be a torch.ByteTensor`로 거부한다. 연구 코드의 잠재 결함이며 CPU에서는 재현되지 않는다. `src/`를 고치면 코드 해시가 바뀌므로, 탐색 스크립트가 체크포인트 로드 직후 RNG 상태 텐서만 CPU로 되돌리는 방식(`rng_state_on_cpu`)으로 우회했다. 모델·옵티마이저·샘플러·커리큘럼 상태는 건드리지 않는다. 실제 체크포인트로 GPU 로드→복원이 되는지 확인한 뒤 재시도했다.
- 1차 시도가 보존한 200k 체크포인트(해시 검증)에서 재개했으므로 200k 단계를 다시 학습하지 않았다.
- **재현성**: 세 언어 모두 v2의 첫 781 업데이트 손실·기울기 노름이 v1 200k 런과 **완전히 동일**(최대 차이 0.0). 커널이 결정적이며 v2의 ~200k 체크포인트는 v1 런의 199,936 노출 시점과 같은 상태다.
- **장부**: 계획 예약 1.0 h(런 3×0.3 + 평가 0.1). 실패한 1차 예약은 실사용(0.058 h)으로 정산되어 재사용할 수 없으므로 재시도 예약 3×0.25 h를 새로 잡았다(명목 예약 합계 1.75 h). 동시에 묶여 있던 예산은 최대 0.908 h로 1 GPU시간을 넘지 않았다. **실제 사용 0.268 h** = 학습 0.254 h(실패 시도 0.058 h 포함) + 평가 0.014 h. 장부 누적 0.665 / 672 GPU시간, 열린 예약 없음.

## 해석 (탐색적, 범위 제한)

- **학습량은 EN/DE의 학습 문항 적합에 결정적이었다.** v1에서 200k까지 ln2 근처에 머물던 EN 손실은 300k 이후 떨어져 600k에 0.19, 900k에 0.06이 되었고, DE는 600k까지도 0.68이었다가 900k에 0.26으로 늦게 떨어졌다. KO는 200k 시점에 이미 0.14였다. 세 언어의 순서는 KO ≫ EN > DE로, 같은 설정에서 최적화 속도가 언어(표현)별로 크게 다르다.
- **같은 평서문 틀 안에서는 새 의미 조합으로 일반화한다** — EN 공간을 빼고. EN 역할·부정·수량과 DE 부정·수량은 학습 표본 정확도와 평서문 dev 정확도가 거의 함께 오른다(차이 0.01–0.07). KO는 300k에서 전 과제 ≥0.94.
- **EN 공간은 학습 표본은 암기(0.93)하지만 평서문 dev로 옮겨가지 않는다(0.56–0.59)**. 혼합 런(0.55)과 순차 런(v1 진단 0.51–0.52)에서도 같았다. 학습량 문제가 아니라 EN 공간 과제의 표현이나 데이터 구성 문제일 가능성이 높으며, 별도 조사가 필요하다. DE 공간·역할도 900k에서 평서문 0.58–0.72로 뒤처진다.
- **외곽 틀 전이는 학습량으로 해결되지 않았다.** 원본 dev A/B는 모든 언어·과제·학습량에서 0.46–0.55이고, 정기 패널 최고치도 0.56 이하다. 900k에서도 숙달 판정은 없다. 이 결과는 v1 문장 틀 진단(`reports/FRAME_DIAGNOSTIC_V1.md`)과 일치한다.
- 위 평서문 수치는 외곽 틀 보류를 완화한 진단이므로 숙달 판정이나 확증 평가가 아니며, 임계값·언어별 설정 선택에 쓰지 않는다.

## 후속 필요 사항 (사용자 작업 요청 아님, 기록용)

- `src/flystudy/train.py` resume 경로의 RNG 상태 장치 결함은 실제 장애 복구에서도 그대로 발생한다. 수정하면 코드 해시가 바뀌므로 G0/G1 재검증 절차와 함께 다뤄야 한다.
- 후속 데이터 설계에서는 같은 표현 분포의 일반화와 미학습 외곽 틀 전이를 분리하고, EN 공간 과제를 별도로 점검한다.
